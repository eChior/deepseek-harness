# @deepseek-ai/dsh-redaction

[English](README.md) | 中文

## 概述

会话会原样保存你给它的东西，所以在模型边界上脱敏为时已晚：消息一旦被接受，harness 立刻把它写进持久日志。本提供者改为在提示词仍是准入结果时改写它。词表的每一处命中都会变成一个形如 `[<标签>-<n>]` 的稳定占位符，同一个值永远映射到同一个占位符，调用方接着把改写后的内容交给下一环。对应关系保存在内存中，并在会话结束时追加到本机的一个映射文件里 —— 恢复工具据此把原文还原进导出文件，重启后再遇到同一个值也仍然用它原来的那个占位符。

## 使用本包

挂载本插件，然后对准调用方即将组成消息的那些部分调用 `redact()`：

```yaml
- id: redaction
  name: '@deepseek-ai/dsh-redaction'
```

### 配置

| 字段 | 默认值 | 含义 |
|---|---|---|
| `termsPath` | 本包内的 `assets/terms.yaml` | 本构建自带的词表；缓存没有可用词表、或缓存比它旧时使用。 |
| `remote` | 内网 Gitea 上发布的词表仓库 | 缓存刷新所拉取的归档地址；设为空字符串即关掉一切网络请求。 |
| `branch` | `main` | 从哪个分支拉取归档。 |
| `file` | `terms.yaml` | 读取归档里的哪个文件。 |
| `cacheDirectory` | `$DSH_HOME/redaction` | `current`、`terms-<revision>.yaml` 与 `terms.fallback.yaml` 所在目录。 |
| `refreshMinutes` | `5` | 后台拉取的间隔分钟数；`0` 表示不轮询，只用手上已有的词表。 |
| `timeoutMs` | `3000` | 单次拉取的请求超时。 |
| `vision` | `true` | 对进入会话的图片做本地识别，并用脱敏后的文本替代。 |
| `visionTimeoutMs` | `20000` | 单张图片超过这个时长就放弃，改用阻断标记替代。 |
| `includeRoster` | `true` | 把随包分发的员工名单里的每个人名与部门名加入规则，并让上传的词表从中继承部门。 |
| `rosterPath` | 本包内的 `assets/roster.bin` | 员工名单的密文；开启它的密钥是 CI secret，打包时写到它旁边的 `assets/roster.key`。 |

没有任何字段可以关掉本提供者。被关掉的提供者写进会话日志的，正是本功能存在意义所要挡住的那些值，而且是悄无声息地写；因此误伤的规则改在词表发布侧修，那次修正会随各机器的下一次刷新自动到位，不需要重装，也不需要改这里。

`redact(parts)` 复制整个列表，只改写 `type` 为 `text` 的部分。图片、文件引用以及其它任何部分都原样返回，因此调用方可以把结果当作原始输入一样交给下一阶段。`redactText(text)` 对单个字符串做同样的事。

图片永远不会以像素形式到达模型。本包同时也是附件库调用的识别器：它读出进入会话的图片里的文字，对文字脱敏，再把文本交回去替代图片部分。全程不写磁盘；识别失败或超时，用阻断标记替代图片。若调用方自己掌管附件准入，把识别器传下去即可 —— `admitPromptContent(parts, ctx.get('redaction'))` —— 子代理读取的图片也会得到同样处理。

`restore(text)` 把本进程发出去的占位符换回其原值。它属于人阅读文本的地方，绝不能出现在写入会话的路径上。

`status` 报告所加载词表声明的修订号、来源、包含多少词条与正则、本进程已做了多少次替换、队列里还压着多少条词条申请、有多少份上传词表正在生效、有多少个名单名字正在生效，以及失败详情。读取不了的词表会留下空规则集（也就是什么都不替换），原因保留在 `status.detail` 里，而不是让插件加载失败。

规则最多来自三个来源，`status` 会把各自的贡献分别计数。已发布词表是底线。它之上是本机上传的词表 —— 某个部门知道而发布端不知道的东西 —— 以及以密文形式随包分发在 `assets/roster.bin` 的员工名单，`includeRoster` 打开时它的同事名与部门名会进入规则。两个来源以相同长度命中同一段文本时，靠前的来源胜：上传胜过名单，名单胜过已发布词表。名单读不出来只记一条告警并跳过，绝不致命中止，也绝不写进 `detail` —— 一台没有密钥的机器照样脱敏其它一切。

`identify(account)` 回答名单里怎么记某个人，`attributionFor(account)` 把它收敛成上传应带的 `{ department?, author? }`，`rosterSummary()` 报告名单是否生效、里面有多少人多少个部门。名单里没有这个名字时只给上传人：部门从不猜。

词表也可以在本机上传，格式相同，供部门补上已发布词表覆盖不到的部分。`localFiles()` 列出本机持有的文件 —— 包含编译不过的那种，因为要看到哪里写错的人正是它的作者 —— `importLocal(name, text, attribution)` 给它打上作者的部门、存盘并使其生效，`removeLocal(name)` 删掉一个，`setLocalEnabled(name, enabled)` 只切换启用状态、不动文件声明的内容，`localExample()` 交回本构建随包附带的带注释示例。上传存放在 `cacheDirectory` 下的 `local/`，最多 `MAX_LOCAL_FILES` 份，每份不超过 `MAX_LOCAL_BYTES`；文件名会被规范化进该目录，因此名字无法指向磁盘上的其它位置。会覆盖整段样例提示词的正则在文件被接受之前就被拒：正是这一点挡住了「一次好意的编辑把每条请求都变成一个占位符」。

词表里缺的词条可以主动申请，而不是干等。`requestTerm(term, note)` 把它追加到 `cacheDirectory` 下的队列，`deliverRequests(sink)` 把队列里每一条待投递申请交给部署自己提供的 `TermRequestSink`。本包不带任何 sink：没有投递目标的机器会把申请留在 `pending` 状态，而不是丢掉；每次投递都会把每条申请落定为 `uploaded` 或 `rejected`，并记下 sink 给出的原因 —— 队列记录发生了什么，而不是让条目凭空消失。

<a id="understand-the-implementation"></a>
## 了解实现

插件通过 `cacheDirectory` 解析自己的词表。名为 `current` 的指针文件记录正在使用的修订号，`terms-<revision>.yaml` 保存该修订的正文，`terms.fallback.yaml` 保留上一次成功加载的词表。拉取失败时手上的词表不受影响，稍后重试，因此连不上内网的机器仍会用已有词表继续工作。本构建自带的词表，如果修订号是一个更晚的日期，就胜过缓存里的那份，因此升级安装包不会被上一版留下的缓存悄悄抵消；不读作日期的修订号则让缓存继续生效。加载过程从不抛错：文件缺失、结构有问题、正则无法编译，都只会让规则集为空并把原因写进 `status.detail`，因此即使部署随包带来一份坏词表，脱敏只是不生效，原因始终可见。

`terms.yaml` 的每一个条目，要么是词条 —— 按字面匹配，转义后才变成正则 —— 要么是正则，按原样编译。同一段文本常常同时命中多条规则，所以写入之前先把命中收敛成互不重叠的一组：先取最长匹配，再比类别优先级（`identifier` 高于人名），最后取更靠左的。因此长编号里的一段数字不会产生第二个占位符。

占位符的身份记录在 `RedactionMap` 里，而不在匹配代码里。某个值第一次出现时，为它所在类别分配下一个序号，之后同一个值继续复用该占位符 —— 模型读工具结果或后续轮次时，可以把 `[编号-3]` 当成同一件事来追踪，却始终看不到它代表什么。会话结束时，这张映射会写进本机的映射目录里；整个机器一个文件，而不是每个任务一个 —— 占位符在哪儿读都是同一个值，所以几周没打开的会话仍然能显示原文。启动时会把它读回来，这也是新值不会拿到上一个进程已经发出去的编号的原因。

占位符只在模型不动它的时候才安全，而对一个被要求总结或翻译的模型来说，一个方括号里的词看起来就是普通文本。所以本插件还注册了自己的一段提示词 `redaction:placeholders`：声明方括号占位符是正常文本，正文与总结中都要逐字照抄；用户问起某个占位符时，要按当前材料作答而不是去查或还原它的原文；同一组的两种写法在总结时可以合并；规则冲突时以逐字照抄为准。这条指令放在系统提示词里而不是设置页，因为需要读到它的是模型；它无条件注册，因为本提供者没有关闭开关：只要一个会话里带着占位符，就永远需要那条保住它的规则。

词表的读取器是一段小扫描器，而不是通用的 YAML 依赖。格式本身是扁平子集 —— 顶层标量、一个类别列表、每类两个字符串列表 —— 扫描器就是全部。

<a id="model-experience"></a>
## 模型体验

间接地，经由调用方交给 `redact()` 的提示词文本：模型看到的是本提供者发出的占位符，而不是那些值本身，其中包括被收敛成 `[人名-2]` 或 `[部门-1]` 的同事与部门；其余面向模型的判断都由调用它的消费者负责。

#### KV 缓存影响

把值换成占位符会改变请求的字节，因此一次会话里第一条被脱敏的提示词无法复用此前已缓存的相同前缀。会话内部前缀保持稳定，因为同一个值永远得到同一个占位符。

## 已知限制与待办

<a id="known-limitations-and-deferred-work"></a>

**运行时不变式：** 不发布运行时不变式伴随包：本服务只拥有一个规则集、一个状态记录和一张内存映射，对它们的观察不可能出现第二个互相矛盾的来源。

- **覆盖范围取决于已接线的调用方** —— 本包只改写调用方交给它的文本，因此提示词准入、工具结果、图片附件之所以被覆盖，是因为这些调用方会经过它。自己拼好文本直接写下去、没有调用 `redact()` 的路径仍未被覆盖，助手自己生成的回复也从不改写。
- **词条申请本身没有投递目标** —— 队列只保存本机投不出去的东西，`deliverRequests` 需要部署提供一个 sink。本包自身不会把任何申请送达发布方，因此没有 sink 的安装只会不断累积申请，而不是把它们发出去。
- **占位符活不过本进程** —— 映射只存在于内存，重启后无法还原上一进程发出的占位符，会话里保留的就是占位符。
- **容器格式仍然不透明** —— 扫描看到的工作簿、演示文稿或 PDF 是压缩字节而不是文本，必须先解包再匹配内容。
- **词表在本仓库之外维护** —— 本包只携带一份供构建起步的副本；维护中的词表单独分发，运行时替换它。
- **员工名单是打包那一刻的快照** —— `assets/roster.bin` 在打包时封存，因此入职、离职、调岗的同事只有等到下一次发版才会体现。名单里没有的名字只能归到上传人自己名下；离职同事之所以退出规则，只是因为那份快照里 `active` 为 false。
- **名单密钥不属于产物** —— 密文随包走，密钥是 CI secret，因此漏掉那一步的安装、或根本没配 secret 的构建，加载不到任何名单。这只会告警、不会失败：其余来源照常生效。
- **上传无法手工指定归属** —— 上传的部门来自名单与当前登录账号，因此共用登录或不在名单里的名字会把文件归到「无部门」，也没有任何方法可以覆盖它。
- **上传是按机器隔离的** —— `local/` 目录属于某一次安装，这里不会把词表分发给同事、不会检查别的机器是否已有同一份，也不会合并同一部门的两份上传。
- **上传从不与已发布词表对账** —— 某条部门规则与已发布规则重复、抢先或遮蔽了它时，照样编译、照样计数，不会留下任何提示；也就是说一次上传可以让同一段文本上的一条已发布规则失效，却不说出来。
