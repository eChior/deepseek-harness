# 提案改善：引导或填表，最后出一份 Excel

**全部用 AskUserQuestion 问答推进，每轮最多 4 问。分两步走：**

1. **第 0 轮——分流 + 挖掘。** 先问一句用户属于哪种情况，不知道提什么的先帮他挖出来。
2. **第 1~3 轮——问全细节。** 事情定了，把十五个格子需要的信息问齐。

最后整理成 JSON、跑脚本、出填好的 Excel。不要开放式聊天问需求，也不要一次把问题全抛出去。

**出 Excel 和交台账是两回事。** Excel 问完就给；**台账只收已经实施完成、提案人自己确认效果达到的提案**——没做完就先不交（见"问完做什么"第 5 步）。

## 铁律

1. **不编造数据。** 用户没给数字就让他在选项里挑"没有数"，补不到就填 0，并把理由写进"计算方式"格。
2. **提案的是"改变做法"，不是"完成本职"。** 判据只有一条：**做法变了没有**。"我按时完成了产量汇总表"不是提案；"把手工汇总改成公式自动汇总，每月省 4 小时"才是。
3. **每个问题都要给 2~4 个常见情形做选项**，让用户挑或者用 Other 改写。开放式空问（"你的改善是什么"）用户答不上来——选项本身就是提示，要写得像他那行的说法。
4. **一事一议。** 多件事打包进一张表，每件都讲不透；拆成几份报。
5. **描述简洁。** 每格只有几十字，写事实和数字，不写"提高效率""加强管理"这类套话。
6. **涉 GMP / 法规 / 安全的改动先走变更控制**，把编号写进"改善对策"格；未批准的不能写成"已完成"。
7. **台账只收已确认完成的提案。** 多维表格台账是"完成登记"：交进去就意味着这件事**已经做完、效果达到**，并且会占用一个流水号。**没做完不交**——先把 Excel 交给员工留存，等他做完再回来提交。

## 第 0 轮之一：先分流

问一句：**"你是已经有具体想提的事，还是想找找有什么可以提的？"**

- 有具体事 → 直接进第 1 轮。
- 没有 / 不确定 → 走下面的挖掘，挖出候选后再进第 1 轮。

## 第 0 轮之二：帮他挖出可提的事（4 问）

大多数人不是没有改善，是**不认为自己做的那点事算改善**。四个问题依次问，命中率从高到低：

| 问什么 | 挖什么 |
|---|---|
| 你工位、电脑或文件里，有没有哪些东西是**你自己弄的**、跟标准或跟别人不太一样、但你觉得更好用的？ | 自制表格/模板/公式/小工具、摆放调整、防错小机关 |
| 这几个月，哪件事比过去省时间了，或者差错变少了？ | 步骤减少、不用再翻找往返、差错下降 |
| 你明天请假一周，接你班的人最容易在哪件事上出错、变慢或根本接不上？ | 你一直在默默兜着的事，兜底办法往往就是改善 |
| 你平时最常吐槽的是什么？为它改过什么吗——哪怕是自己偷偷改的。 | 吐槽旁边那句"我自己改了下"才是提案 |

每问的四个选项（痕迹法 / 对比法 / 接班法 / 吐槽法）、挖出来之后怎么让用户挑、四问都没挖出来怎么办、门槛怎么说清楚、哪些要先劝退，见 `references/question-flows.md`。

**挖出来以后**：勾中的每条都写成一句候选（"你把××从××改成了××"），列 2~3 条让用户挑一条，然后进第 1 轮。**用户挑中的那条，往往已经把第 1 轮的前两问答了——别重复问。**

## 第 1 轮：事情本身（4 问）

| 问什么 | 填到哪 |
|---|---|
| 改善前是什么情况、原来怎么操作的？ | 存在问题 |
| 原来的做法带来什么损失（费时间 / 容易错 / 有风险 / 功能受限）？ | 存在问题、无形效益 |
| 你具体做了什么？（关键动作、谁做的、什么时候、花没花钱、走没走审批） | 改善对策 |
| 为什么原来不行，卡在哪？ | 主要原因 |

三组选项（改善前 / 具体做了什么 / 卡在哪）见 `references/question-flows.md`。

## 第 2 轮：效益与固化（4 问）

| 问什么 | 填到哪 |
|---|---|
| 现在比原来好了多少？有没有可量的数字（次数 / 时间 / 差错）？ | 无形效益、计算方式 |
| **这项改善每月能省下多少小时？** | **月度效益（台账必填列，只填一个数字）** |
| **这项改善省下多少时间，或者带来什么量化效益？具体数字是多少？** | **量化效益（台账必填列）** |
| 有没有省下钱或减少支出？ | 经济效益 |
| 怎么防止反弹？ | 控制措施 |
| 有没有形成文件或编号？ | 成果标准化 |

**"本来要买没买"这笔最容易被漏掉，要专门问一句。** 五问的选项见 `references/question-flows.md`。

**月度效益是必答项，而且必须是数字。** 这一列只填一个数：每月省下多少小时（可带一位小数，例如 `4` 或 `2.5`）。算得出来就问清楚"每月"这个口径——一天省 0.2 小时按 20 个工作日算就是 4；确实算不出来就写 `0`，**不要留空、不要带单位、不要写文字**，台账靠这一列求和出月度总效益。

**量化效益是必答项，但只要求"表态"，不强制有数字。** 先帮他算：节省工时（小时/月 或 小时/年）、减少次数、降低不良率、少采购几件、少跑几趟。算得出来就写成 `节省工时：<数字> 小时/月；<其他量化>`；确实算不出来就写 `没有量化指标`（也可以写"没有"）——**不允许留空，也不允许替他编数字**。这一问的价值在于逼他想一遍，结果是不是"没有"由他判断；评审看的是这一列有没有交代，不是非要有数字。

## 第 3 轮：署名、证据、完成情况、提案类型（6 问）

| 问什么 | 填到哪 |
|---|---|
| 提案人、实施人怎么署名？完成日期填哪天？ | 提案人、实施人、完成日期 |
| 改善前和改善实施的照片（或截图）有没有？ | 照片两个位 |
| 这项改善的属性是什么？（新增 skill / 程序脚本 / 改流程 / 改设备物料 / 其他） | 提案类型，并决定「AI相关」打不打勾 |
| 这件事属于哪类业务？ | 业务类型 |
| **这项改善实施完成了吗？效果达到了吗？** | **决定能不能交台账** |

**只有"已经做完、效果就是预期的"才提交台账**（②③把 Excel 交给他、等做完再说；④回第 0 轮重新挖，或如实劝退）。这一问不能省：它把"填完表"和"事情做完"分开。

署名 / 照片 / 提案类型 / 业务类型 / 完成情况六问的选项，以及照片的写作口径、改善前没留证据怎么办、提案类型的七个选项，见 `references/question-flows.md`。

## 问完做什么

1. **拟提案名称**（≤22 字：改了什么 + 对象 + 效果）。从第 1 轮的答案里提炼。
2. 把答案整理成 JSON，跑：

   ```bash
   python "$SKILL_DIR/scripts/make_proposal.py" 提案.json --out ./提案改善
   ```

   得到 `改善提案报告-<名称>.xlsx`（十五格已填、照片已嵌入）。脚本打印的"填写提示"照读给用户。第一次用 `--new 提案.json` 生成空白 JSON 模板，`--fields` 看字段与每格字数上限。
3. **回报三件事**：哪些句子是你按常规推断的（请用户核对，**技术做法尤其要核对**）；哪里还是占位符（姓名、照片占位图）；提醒双击格子换照片。
4. **打开生成的 Excel 让用户过一遍，确认每个数字他都认**——他要在初评栏签字。
5. **交台账——这是结案动作，不是填完表就交。** 台账只收**已实施完成、提案人自己确认效果达到**的提案。拿不准就再确认一句："这项改善现在做完了吗？效果是你预期的那样吗？"

   已确认完成 → 跑 `scripts/submit_bitable.py`（`--done` 是结案确认开关，不加它会拒绝执行）；**还没完成 → 不要跑提交脚本**，把 Excel 交给用户留存，等做完再回来提交。

   台账的「AI相关」复选框**默认不打勾**。只有第 3 轮问出这项改善属于「新增了一个 skill」或「写了程序 / 脚本 / 自动化」时，才给提交命令加 `--ai-related`；改流程、改制度、改设备、改物料、改工装的一律不勾。

   完整命令、脚本自动填的字段、授权码的实情、手工提交路径与 `--record-id` / `--dry-run` / `--token` / `--ai-related` 等开关，见 `references/ledger-submit.md`。

## 表单十五格与效益写法

**这是一页纸摘要。** 每格字数很紧，写不下就把细节放附件。十五格逐格口径、效益计算公式（工时 / 物料 / 能耗 / 质量损失 / 投入）、工时折钱的三条前提、扣成本与年化依据、计算方式格只写一行的写法，见 `references/form-fields.md`。
